Context Graph

Understand it before you change it.

An agent works out what good looks like from whatever it happens to read, and forgets it when the session ends. Context Graph keeps the why in git, beside the code: a card for every file, the rules each module follows, and the decisions made on them. It hands the agent the right slice at the moment it edits, and refuses the edit until the file is understood.

The context loop

For every edit of a file:

  1. Is the file understood? Its card is fresh, or the agent read it in full this session along with what it imports. If the edit changes what the file exports, its importers too. If not, the edit is refused, naming each file to read and why.
  2. The edit, with the slice: the file's card, the rules that apply, and the decisions made on it and on what it imports.
  3. The card is owed: what the file is for, what it relies on, who relies on it, what it must keep true. A decision is recorded for each constrained file before the turn ends.

The graph

A small graph in .ctx/, committed with the code: modules mapped onto your paths, concepts, rules (agreed, guidance or proposed), decisions with who made them and why, and cards with each file's content hash, so a card is fresh only while the file is unchanged. /context-graph:init proposes the graph from your tree, tests, instruction files and ADRs, and nothing is enforced until you agree it. A person ratifies rules with a commit trailer agents may not write.

In the session

  • The Context pane follows the file an agent is on: its card as Markdown, its rules as chips, its decisions and its neighbourhood. /graph <path> opens it on any file.
  • Proposals in plain words: Accept, Reject or Later, grouped by module, with the evidence for each.
  • The card writer writes owed and missing cards in the background, from full reads. With a backfill, it cards a brownfield codebase, leaves first.
  • The curator reads the decisions and proposes the rules they keep making, and flags rules overridden again and again.
  • /why answers a question beside the conversation, from the graph's records only, citing each one.
  • The Map tab draws the modules as a graph: rules, coverage, decisions pulsing in.

With code-kit

Each knows the other through an adapter, and neither imports the other's code. With code-kit present, a card names the spec requirement its file delivers and the file's lane and layer, so the layer rule is in front of the agent before it drafts an edit. code-kit lets every agent write cards and decisions, keeps the graph's rules the lead's, and shows each lane's understanding in its own pane. Pausing code-kit's loop pauses the card writer and curator too.

Commands

/context-graph:nextLook at the repository and take the next step.
/context-graph:initPropose a graph, set the ratifiers, and offer the backfill.
/graph · /why · /graph-settingsThe Context pane, a side question, the harness settings.
ctx card <path> --textWrite or update a file's card.
ctx why · ctx historyA node's decisions and rules, now or over time.
ctx hydrate <scope>One briefing before work: slices, callers, rules with history.
ctx cards --backfillWhat a brownfield backfill would card, leaves first.
ctx gate --base origin/mainIn CI: ratification, stale cards, opposed decisions.
ctx doctorIs it working here, and which link is missing if not.

When to use it

When the codebase has rules the code doesn't state, decisions get lost, several agents or sessions work on the same code, or you want evidence of how an agent worked. It costs something: enforced reading and cards took about 2.5 times the time and tokens in the benchmark. For a throwaway script, leave it observe-only or don't give the repository a graph.
